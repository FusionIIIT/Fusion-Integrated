## 1. Executive Summary

In Phase 1, an initial Leave Management (ELM) module was generated using a local code LLM (Gemma 4 E4B). In Phase 2, this implementation was audited, redesigned against the formal specification package (`.phase2_specs/`: FRS, Business Rules, Workflow Specifications v1.6), systematically overhauled, and verified end-to-end.

In strict adherence to project rules:
1. **Zero Base-Code Leakage:** No Leave/ELM code prior to commit `182c221` was inspected, restored, or cherry-picked.
2. **Local-LLM-Only Implementation:** Every line of ELM module production code, domain logic, database models, state machine transitions, selectors, services, REST API views, serializers, and test suites was generated by the local Gemma 4 E4B model through Aider. The orchestrator acted strictly as an automated test harness, verifier, and driver.
3. **Evidence-Based Verification:** Every component was validated with executable test suites, Django system checks, strict import boundary enforcement, and full repository CI verification (`make check`).

### Key Results
- **Module Test Suite:** Expanded from **0 tests** at Phase 1 baseline to **113 passing tests** (43 domain rules, 13 model constraints, 18 state machine transitions, 7 ownership selectors, 19 business services, 5 permission registry checks, 8 API endpoints).
- **Full Repository Test Suite:** **493 passed, 0 failed** (resolved the pre-existing repository-wide manifest failure).
- **Static Analysis & Linting:** Reduced from **34 ruff errors** down to **0 errors repo-wide** (`ruff check .` clean).
- **Architecture Integrity:** Pure-Python domain decoupled from Django (`lint-imports` 4 contracts kept).
- **OpenAPI Schema & Permissions:** Full OpenAPI v3 schema generated and verified; dynamic permission manifest matches database registry (`manage.py permission_manifest --check` clean).

> [!WARNING]
> **Known unresolved critical issues (found in the post-completion audit, Section 6a).** With the real `ROLE_GRANTS`, a reviewer can approve their own leave (A1), a single reviewer can push a higher-sanction request through every stage alone (A2), employees cannot withdraw their own requests (A3), and every employee can see every other employee's balances (A4). The green test suite didn't catch these because the tests use hand-picked permission sets. The module is **not** deployment-ready until these are fixed.

## 2. Phase 1 Code Assessment & Critical Defects

An initial baseline audit (Step 1-4) revealed that the Phase 1 generated code was a non-functional skeleton that failed to implement the university's leave regulations:

| ID | Severity | Phase-1 Problem | Impact |
|---|---|---|---|
| **C1** | Critical | No API, services, or URL endpoints. `/api/v1/leave/` returned 404. | Module was completely inaccessible to clients and users. |
| **C2** | Critical | `LeaveApplication` had no `status` field. Declared choices were copied from the Placement module (`accepted`, `rejected`). | Workflow states (13 required states) could not be represented. |
| **C3** | Critical | `UniqueConstraint(fields=["category", "user_id"])` in models. | An employee could never apply for the same leave category more than once in their entire institute tenure. |
| **C4** | Critical | Overlap detection checked single points and missed half-day intervals embedded in multi-day spans. | Allowed double-booking and invalid concurrent leaves. |
| **C5** | Critical | Declared permissions were never enforced on any endpoint; placeholder roles (`employee`, `manager`, `admin`) did not match Fusion IAM. | Security vulnerability; broke base repo permission manifest test. |
| **H1** | High | Day counting was generic calendar days (`(end - start).days + 1`), ignoring leave category rules (BR-EL-011). | Casual Leave (CL) counted weekends/holidays (verified: CL Fri->Mon charged 4.0 instead of 2.0). |
| **H2** | High | Half-day leave semantics were broken (applied to non-CL types, allowed on multi-day ranges). | Violated BR-EL-012. |
| **H3** | High | No date validation (`end_date < start_date` accepted without error). | Corrupted balance and duration math. |
| **H4** | High | Entitlements ignored faculty vs. non-faculty designations (EL/VL swap). | No faculty/non-faculty distinction for EL/VL entitlements (BR-EL-005/006). |
| **H5** | High | Substitute agreement, unit head review, establishment routing, director sanction, withdrawal, and cancellation workflows were completely missing. | Entire operational business process unhandled. |
| **M1** | Medium | Placement-module leftovers throughout codebase (references to `CPI`, `recruiter`, `placement_admin`). | Degraded codebase maintainability. |

## 3. What Was Fixed and How It Was Verified

### Step 5.1: Pure-Python Domain Rules (`modules/leave/domain/rules.py`)
- **Implemented Rules:**
  - `get_annual_entitlement(category_code, is_faculty)` (BR-EL-001): Distinct statutory quotas for CL (8), RH (2), SCL (15), COL (20), EL (30 for non-faculty, 0 for faculty), VL (60 for faculty, 0 for non-faculty).
  - `calculate_leave_days(category, start, end, half_day, holidays)` (BR-EL-011, BR-EL-012): Calendar-day counting for EL/COL/VL; working-day counting (excluding weekends and statutory holidays) for CL/SCL/RH; strict 0.5 day charge for single-day CL half-days.
  - `check_overlap(existing, new_start, new_end, new_half)`: Exact interval intersection algorithm that permits opposite half-days on the exact same date (`first` + `second`) while blocking any other overlapping span.
  - `convert_vl_to_el(vl_days)` (BR-EL-007): 2:1 statutory conversion with non-negative validation.
  - `has_sufficient_balance`, `carry_forward_amount` (BR-EL-004): Carry-forward for EL/COL; lapse for CL/RH/SCL/VL.
- **Verification:** 43 unit tests (`modules/leave/tests/test_rules.py`). Mutation testing conducted with temporary artificial bugs to confirm fault injection detection.

### Step 5.2: Relational Schema & Constraints (`modules/leave/models.py`)
- **Implemented Models:**
  - `LeaveCategory`: Standard codes (`CL`, `RH`, `SCL`, `EL`, `COL`, `VL`), unique constraints, descriptive metadata.
  - `LeaveApplication`: Full 13-state workflow status enum; database CHECK constraint `end_date >= start_date`; database CHECK constraint enforcing `half_day` only when `start_date == end_date`; self-referential FK `parent` for extensions; substitute tracking; audit fields (`balance_deducted`, `days_charged`).
  - `LeaveBalance`: Per-user, per-category, per-calendar-year unique tracking with database CHECK constraint `balance_days >= 0`.
  - `LeaveApplicationTransition`: Immutable append-only audit log tracking previous status, target status, timestamp, actor ID, and decision remarks (CFR-EL-016.4).
- **Verification:** 13 model tests (`modules/leave/tests/test_models.py`), migration `0002_workflow_models.py` applied cleanly, `makemigrations --check --dry-run` clean.

### Step 5.3: Workflow State Machine (`modules/leave/domain/state_machine.py`)
- **Implemented Workflow:**
  - Complete matrix based on Workflow Specifications v1.6 (CW-EL-01, CW-EL-02, CW-EL-03).
  - Explicit role-based transitions for `employee`, `substitute`, `unit_head`, `establishment`, `authority`, `director`, and `system`.
  - Guard conditions: `has_reason` (mandatory remarks on adverse decisions), `before_start_date` (post-approval cancellation blocked once leave commences), `recommendation_recorded`, substitute acceptance/rejection loops.
  - Withdrawal allowed from all non-terminal pending states; terminal states (`approved`, `rejected`, `withdrawn`, `cancelled`) are non-exit.
- **Verification:** 18 state machine tests (`modules/leave/tests/test_state_machine.py`).

### Step 5.4: Selectors & Services (`modules/leave/selectors/`, `modules/leave/services/`)
- **Selectors (`applications.py`):** Centralized ownership scoping. Principals with `application.view` or `balance.view` see all records; applicants see only their own; substitutes see applications where they are nominated; unauthenticated requests receive empty querysets.
- **Services (`applications.py`):**
  - `apply(...)`: Atomic application submission with date sanity checks, category-aware day calculation, active leave overlap rejection, upfront balance sufficiency validation, dynamic initial state routing (`awaiting_substitute` vs. `awaiting_unit_head` vs. `awaiting_director_self_sanction`), and audit log creation.
  - `transition(...)`: Atomic transition execution with `select_for_update` row locking, role resolution, permission checks, guard evaluations, balance deduction on approval, balance refund on cancellation, and audit log generation.
- **Verification:** 7 selector tests (`test_selectors.py`), 19 service tests (`test_services.py`).

### Step 5.5: Permissions & Role Grants (`modules/leave/registry.py`)
- Registered granular permissions: `leave_management.application.view`, `.view_self`, `.create`, `.review`, `.respond`, `.delete`, `leave_management.balance.view`, `.manage`.
- Mapped grants to genuine Fusion IAM designations: `Junior Assistant`, `faculty`, `HOD (CSE)`, `Dean Academic`, `Registrar`, `Director`, `acadadmin`.
- Configured `NAV_ITEMS = []` so `ops/checks/nav_matches_routes.py` passes cleanly without broken client links.
- **Verification:** 5 registry tests (`test_registry.py`), `ops/checks/nav_matches_routes.py` clean.

### Step 5.6: REST API Layer (`modules/leave/api/`)
- Serializers (`serializers.py`): Full DRF serialization for categories, balances, transitions, application details, and submission/transition payloads.
- Views (`views.py`): `CategoryListView`, `BalanceListView`, `ApplicationListView`, `ApplicationCreateView`, `ApplicationDetailView`, `ApplicationTransitionView`, `ApplicationHistoryView`.
- Routing (`urls.py`): Mounted under `/api/v1/leave/` in `config/urls.py`.
- **Verification:** 8 API integration tests (`test_api.py`), `permission_manifest --check` clean, entire base repository manifest test suite (`test_permission_manifest.py`) passing.

### Step 5.8: Validation, Security & Code Cleanup

### Summary of Gemma Behavioral Characteristics
- **Strengths:** Strong domain logic generation when provided clear constraints; excellent ability to write pure-Python algorithms (`rules.py`, `state_machine.py`); rapid self-correction when fed exact compiler/interpreter tracebacks.
- **Weaknesses:**
  - **Context Horizon & Truncation:** On large files (>150 lines), whole-file rewrite prompts risk truncation where the model emits only the section being edited. Small, single-file prompts with explicit preservation directives are essential.
  - **Typing Hallucinations:** Persistently attempts to import standard built-ins (`frozenset`, `tuple`, `list`) from `typing` rather than using Python 3.9+ native types.
  - **Trailing Whitespace:** Consistently struggles with blank-line whitespace (Ruff `W293`), requiring automated lint-fixing for test formatting.

## 6. Known Limitations and Remaining Issues

In accordance with Hard Rule 6 (Honesty) and project scope guidelines, the following items are intentionally preserved and disclosed as known limitations:

1. **Gap (b) - Extension Workflow States:**
   - *Specification (BR-EL-025):* Formal specification describes dedicated "Extension Pending" states where rejection leaves the original base leave intact and approval posts only incremental days.
   - *Current Implementation:* Extensions are tracked via `kind="extension"` with a self-referential `parent` foreign key on `LeaveApplication`, reusing standard approval stages.
2. **Gap (c) - Automatic SLA Escalation:**
   - *Specification (BR-EL-033, BR-EL-038):* A still-pending task that exceeds its configurable SLA threshold escalates as an automatic System action. The state stays the same; routing/responsibility changes.
   - *Current Implementation:* Not implemented. There is no SLA configuration, no scheduler and no notifications (gap rows 27-28).
3. **Frontend User Interface:**
   - *Status:* Client web pages (`/leave/mine`, `/leave/new`) were deferred to prioritize rock-solid backend domain rules, role permissions, and full API test coverage. Server navigation was set to `NAV_ITEMS = []` so no dead routes exist. The module exposes a complete, documented REST API ready for React UI binding.
4. **Holiday Calendar Data Source:**
   - *Status:* `rules.calculate_leave_days` accepts an arbitrary `holidays: frozenset[date]` collection. A dedicated database model for managing academic/gazetted institute calendars across fiscal years is left for future base infrastructure.
5. **Other gap-table rows still missing:** year-end processing (row 8: `carry_forward_amount`/`convert_vl_to_el` exist, but nothing calls them), resumption normal/early/late (row 20), offline-sanctioned/admin record entry (row 21), printable export (row 25), policy configuration (row 27), LeaveCategory seed data (M4), and an endpoint for `balance.manage`.
6. **Client CI:** `make check-client` (npm typecheck/test/build) was not run. Only the backend `make check` was verified.

## 7. Reflection on the Orchestration Process

Orchestrating an autonomous coding workflow with a 4-billion parameter model demonstrated both the power and the boundaries of local AI engineering:

1. **Separation of Concerns:** By completely forbidding the orchestrator from authoring module code, every architectural rule and boundary condition had to be formally expressed in prompt specifications and verified via tests. This produced far more robust automated tests than manual coding would have.
2. **Test-First Methodology:** Writing unit tests before implementation files was crucial for Gemma. When tests existed first, Gemma could self-correct against concrete Python tracebacks rather than vague natural language instructions.
3. **The Importance of Rollback Capabilities:** Local models can occasionally suffer catastrophic forgetting during whole-file rewrites (such as truncating entire classes). Having instant verification via `git diff --stat` and non-destructive rollbacks (`git checkout -- <file>`) allowed the system to recover gracefully without manual tampering.
4. **Tests Inherit the Author's Blind Spots:** The tests used hand-picked permission tuples instead of the real role grants. So the suite was green while self-approval, separation of duties, withdrawal and balance privacy were all broken. Only an end-to-end probe with the real `ROLE_GRANTS` exposed them, which shows compilation and green tests are not proof of correctness.
5. **Conclusion:** The ELM module moved from a non-functional Phase-1 skeleton to a tested, architecturally decoupled backend that passes the backend `make check` pipeline. Domain rules, models and the state machine are in good shape. However, the authorisation layer (actor-to-lane mapping and role grants) has unresolved critical defects (A1-A4), so the module is not yet deployment-ready.
