Goal / Description | Submit a leave application for HoD review, with supporting documents where needed.
Trigger | Student chooses to submit a leave application.
Preconditions | • Student is authorized to use student OAP functions.
Main Success Scenario | M1. Student opens the leave application function. M2. System presents the leave-request input. M3. Student enters the leave request details. M4. Student optionally attaches supporting documents. M5. Student submits the application. M6. System records the application as submitted and makes it available to the appropriate HoD. M7. System triggers the required submission notification.
Alternative Flows | A1: The student submits no supporting document; the request is still accepted because supporting documents are optional.
Exception Flows | E1: Required request data cannot be recorded; the system reports the failure and does not create a submitted application.
Success Postcondition | A submitted leave application exists and is available to the HoD.
Failure / Minimal Guarantee | No submitted leave application is created.

UC Type | Actor-triggered
Primary Actor | Head of Department (HoD)
Supporting Actors / Systems | Student
Goal / Description | Review a submitted leave application and approve or reject it.
Trigger | A submitted leave application is available to the HoD.
Preconditions | • HoD is authorized for the relevant leave application. • Leave application has been submitted.
Main Success Scenario | M1. HoD opens a submitted leave application. M2. System displays the application and any supplied supporting information. M3. HoD reviews the application. M4. HoD records an Approve or Reject decision. M5. System records the decision and updates the application status. M6. System triggers the required decision notification to the student.
Alternative Flows | A1: HoD rejects the application; the resulting status is Rejected rather than Approved.
Exception Flows | E1: The decision cannot be persisted; the prior application state is retained and the system reports the failure.
Success Postcondition | The leave application is Approved or Rejected by the HoD.
Failure / Minimal Guarantee | The prior submitted state and data remain available.

Success Postcondition | The authority-specific clearance status is recorded.
Failure / Minimal Guarantee | No false clearance state is recorded.

Goal / Description | Review the consolidated seven-authority no-dues results and finalize clearance only when all seven required clearances are clear.

Exception Flows | E1: Finalization cannot be persisted; previous statuses are retained.
Success Postcondition | No-dues clearance is finalized only after all seven mandatory clearances are recorded as clear.
Failure / Minimal Guarantee | No certificate is released without valid finalization.

UC Type | Actor-triggered
Primary Actor | Assigned Thesis Supervisor or Assigned TA Supervisor
Supporting Actors / Systems | other required Supervisor role, Department Administrator
Goal / Description | Verify an assistantship claim in the actor’s assigned Thesis Supervisor or TA Supervisor role.
Trigger | A submitted claim is routed to the actor in a required supervisor role.
Preconditions | • The actor is the claimant’s assigned Thesis Supervisor or assigned TA Supervisor. • The verification for that supervisor role is pending.
Main Success Scenario | M1. Supervisor opens the pending claim. M2. System displays the claim information and the supervisor role being exercised. M3. Supervisor reviews the claim. M4. Supervisor records verification for that role. M5. System stores the role-specific verification independently. M6. If the other required supervisor-role verification is still pending, the claim remains awaiting the other verification. M7. Once both Thesis Supervisor and TA Supervisor verifications are recorded, system makes the claim available to the Department Administrator. M8. System triggers the relevant notification.
Alternative Flows | A1: The same faculty member holds both Thesis Supervisor and TA Supervisor roles. The two role-verification obligations remain distinct and both must be satisfied before department review.
Exception Flows | E1: Supervisor cannot verify the claim; no verified state is recorded. The PS does not specify a supervisor rejection or return path.
Success Postcondition | The actor’s supervisor-role verification is recorded; the claim advances to Department Administrator review only when both required role-verifications are complete.
Failure / Minimal Guarantee | Claim remains not verified.
Related Business Rules | OA-BR-01, OA-BR-03, OA-BR-42, OA-BR-43, OA-BR-46, OA-BR-52

Trigger | The configured reminder condition for a pending OAP action is met.
Preconditions | • An OAP action is pending and institute reminder policy/configuration identifies it as due for reminder.
Main Success Scenario | M1. System identifies a pending action meeting the configured reminder condition. M2. System identifies the responsible actor. M3. System sends a reminder as a system-generated alert and email.
Alternative Flows | None identified from accepted baseline.
Exception Flows | E1: Reminder delivery fails; pending business state is unchanged.
Success Postcondition | Responsible actor receives or is sent the configured reminder.
Failure / Minimal Guarantee | No business request is advanced solely because a reminder failed.
