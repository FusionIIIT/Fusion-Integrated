UC ID | HM-UC-001
UC Name | Create Hostel Record
UC Type | Actor-triggered
Primary Actor | Super Admin
Supporting Actors / Systems | None
Goal / Description | Enable Super Admin to create hostel records in HM.
Trigger | Super Admin opens the hostel master administration function.
Preconditions | • Super Admin is authenticated. / • HM access is permitted under institution-level access and RBAC constraints (BR-HM-003, BR-HM-005). / • The hostel master record to be created does not already exist as the same target record.
Main Success Scenario | • 1. Super Admin opens the create-hostel function. / • 2. The system displays the hostel master data fields required for a hostel record. / • 3. Super Admin enters hostel identification and related master information. / • 4. Super Admin submits the hostel record. / • 5. The system creates and stores the hostel record.
Alternative Flows | None
Exception Flows | • If authorization fails, the system denies or hides the function and makes no business-state change. / • If required data cannot be validated or recorded, the system does not commit the requested change and presents an appropriate message.
Success Postcondition | A new hostel record exists in HM.
Failure / Minimal Guarantee | Existing valid records remain unchanged; no partial intended business-state change is committed.
Related Business Rules | BR-HM-003, BR-HM-005
Related CFRs / AFRs | 
Related Workflow(s) | N/A

UC Name | Manage Warden Role Binding
UC Type | Actor-triggered
Primary Actor | Super Admin
Supporting Actors / Systems | None
Goal / Description | Enable Super Admin to assign, reassign, activate, or deactivate Warden role bindings for hostels.
Trigger | Super Admin opens Warden role binding administration.
Preconditions | • Super Admin is authenticated. / • HM access is permitted under institution-level access and RBAC constraints (BR-HM-003, BR-HM-005). / • The target hostel record exists.
Main Success Scenario | • 1. Super Admin selects the hostel and Warden role-binding action. / • 2. The system displays existing Warden bindings and status for the selected hostel. / • 3. Super Admin enters or changes the Warden binding/status. / • 4. The system records the binding, reassignment, activation, or deactivation. / • 5. The system applies hostel-specific access visibility for the updated Warden role binding.
Alternative Flows | • A1. Super Admin assigns or reassigns the Warden binding. / • A2. Super Admin activates or deactivates the Warden binding. / • A3. Where time-bound role validity is configured in HM, the binding may include the configured start/end validity data; no time-bound rule is inferred when it is not configured (BR-HM-004).
Exception Flows | • If authorization fails, the system denies or hides the function and makes no business-state change. / • If required data cannot be validated or recorded, the system does not commit the requested change and presents an appropriate message.
Success Postcondition | The Warden role binding/status is recorded for the selected hostel. On reassignment, the new role holder can view pending HM records for the assigned hostel subject to BR-HM-006.
Failure / Minimal Guarantee | Existing valid records remain unchanged; no partial intended business-state change is committed.

UC ID | HM-UC-006
UC Name | Record Hostel and Room Allotment Decisions
UC Type | Actor-triggered
Primary Actor | Super Admin
Supporting Actors / Systems | Fusion notification infrastructure / configured notification mechanism
Goal / Description | Enable Super Admin to record hostel and room allotment decisions.
Trigger | Super Admin opens batch allotment or allotment decision recording function.
Preconditions | • Super Admin is authenticated. / • HM access is permitted under institution-level access and RBAC constraints (BR-HM-003, BR-HM-005).
Main Success Scenario | • Super Admin opens the batch allotment / allotment-decision recording function. / • The system displays accommodation records and room/allotment context maintained in HM for the allotment round. / • Super Admin records hostel and room allotment decisions. / • The system checks that the resulting occupancy does not exceed defined room capacity (BR-HM-010). / • The system records the allotment decision, updates room assignment and occupancy information, and retains the resulting room-assignment history (BR-HM-008, BR-HM-009). / • The system issues the supported room-allocation status update/notification to relevant users through the configured mechanism (BR-HM-034).
Alternative Flows | None
Exception Flows | • If authorization fails, the system denies or hides the function and makes no business-state change. / • If required data cannot be validated or recorded, the system does not commit the requested change and presents an appropriate message. / • If the recorded allotment would exceed defined room capacity, the system rejects that update and preserves the prior occupancy state (BR-HM-010).
Success Postcondition | Allotment decisions and related room assignment information are recorded.
Failure / Minimal Guarantee | Existing valid records remain unchanged; no partial intended business-state change is committed.
