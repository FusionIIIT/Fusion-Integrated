## 3.2  -  Domain model, integrity and ownership

**Bounded context:** one HR-EIS module: service-record maintenance and employee HR request lifecycles are tightly coupled through the person's service attributes and effective-dated HR policy. Finance execution, payroll, user provisioning, identity designations, official mail delivery, and institute-wide notification transport are external contexts. HR-EIS only stores its own transaction and status projection.

| Entity / responsibility | Stored fields (non-exhaustive) | Enforcement |
|---|---|---|
| `EmployeeServiceRecord` | unique integer `user_id`, appointment details, department/designation snapshot, service history, retirement status, revision | HR-only optimistic revision updates; no IAM/ERP identity writes |
| `ServiceRecordRevision` | record, revision number, full snapshot, actor/acting designation, timestamp | unique record/revision; append-only database trigger |
| `HRRequest` | `user_id`, family, subtype, state, payload, frozen policy, route step, version, submitted/created/updated times | valid-family DB constraint; service-owned state transitions and owner/role scoping |
| Leave payload in `HRRequest` | subtype is leave type; payload contains duration and justification | six supported types; explicit eligibility; ledger balance checked at submit and final approval |
| `LeaveLedgerEntry` | user ID, leave type, signed quantity, event key, policy, actor, timestamp | append-only; unique event key; final approval locks the employee record before debit |
| `AppraisalDetail` | one-to-one request, employee-record FK, period key, submitted form, reviewer IDs, archive reference, finalized time | unique employee-record/period DB constraint and owner-row lock prevent duplicates; finalization archives into service history; finalized detail immutable |
| `ClaimDetail` | request, claim type/subtype, prescribed LTC form reference or CPDA purpose/amount, HR/financial reviewer, processing details | HR verification precedes approval; separate financial review/status permissions |
| `ClaimDocument` | claim, externally verified attachment metadata | no public upload endpoint; this model does not certify document storage or bytes |
| `ApprovalRouteStep` | request, position, exact designation, policy-version label | unique request/position; frozen route; current-step actor only |
| `HRRequestTransition` | request, source/event/target, actor/acting designation, specification, before/after steps, unique idempotency key, reason, time | append-only database trigger; chronological scoped detail history |
| `HRPolicyVersion` | family, positive 32-bit version, effective interval, parameters, approving actor/role, time | immutable; unique family/version; interval check and per-family publication lock |
| `AuditEvent` | event key, actor/role, subject, action, resource kind/ID, permitted JSON data, time | append-only; atomic with business write; restricted audit selector |
| `Notification` | recipient, optional request, unique event key, title/message, read time | recipient-only dashboard read/mark-read; delivery tracked separately in outbox |
| `OutboxEvent` | unique event key, type, minimal payload, attempts, queued/dispatched times | durable transactionally created event; retryable configured-backend handoff |
| `FinancialStatusProjection` | claim, unique event key, source, external/review references, reported status, attestor, time | immutable history; source/reference/status remain null until a report exists; later reports append history; no money transfer or verified provider integration |

All foreign keys in this table are **within the HR-EIS module only**. Every referenced person is a plain integer `user_id`, never a ForeignKey to an ERP/IAM user table. User-scoped reads begin in `selectors/scoping.py`, which returns not-found (404) when a record is outside the active role's scope. Unique keys and `select_for_update` protect idempotency and double spending; concurrent approval of two requests must not overdraw the ledger. Where the specification omits quantity units, threshold or calendar policy, the corresponding write remains an actionable configuration error, not a hard-coded default.

**Mutability classification:** policy versions, finalized appraisals, service-history revisions, routing/decision history, ledger entries and audit events are append-only. Mutable current-state projections are derived/maintained in the same transaction. Cancellation, deletion, and a "returned for correction" state are **not** introduced without a cited live spec provision.

Basis flows `BW-HR-01..13` are finite paths through these same transition sets and are individually traced in Section 3.1. **Atomic write algorithm:** verify the active role, permission and row scope; lock the request and relevant employee entitlement scope; validate the declared transition, frozen policy and current authority step; update the projection and version; append immutable decision, audit and applicable ledger/status entries; create a durable notification/outbox event; commit. Record edits additionally check the client's expected revision. Appraisal submission locks the employee record before checking the period. A failed business operation rolls back all its writes; other transactions see dashboard notices only after commit.

**State/role caveats:**
- Only the six specified leave types are accepted. Leave rejection does not deduct balance. A forwarding hop does not spend entitlement; only final approval does.
- Appraisal reviews are performed by the configured reviewer/approval hierarchy. The source does not authorize a fabricated rejection/return loop for finalized appraisals.
- Claims are distinct LTC versus CPDA, each with Advance and Reimbursement. HR-verification gates the approval queue; Accountant must check financial correctness before recording settlement status, and **no direct payment is initiated**.
- Each of the 13 basis workflow tests must still independently exercise its named path, even though their transition implementation is shared.
- No guessed reminder frequency or payment settlement duration becomes a clock-triggered transition.

## 3.6  -  Public contracts and external dependencies

Plural, read-only functions in `modules/hreis/contracts.py` serve trusted Fusion
module consumers, with no direct ORM import across the module boundary. These
functions take requested IDs rather than a principal; the consuming module must
authorize its caller before using their projections. They are not HTTP endpoints.
User-facing HR reads instead use `selectors/scoping.py` and its active-role scope.
- `get_employee_service_summaries(user_ids: Sequence[int])` -> minimal trusted inter-module service-record DTOs, no private attachments.
- `get_employee_leave_balances(user_ids: Sequence[int], leave_type: str)` -> ledger-derived balances for trusted module consumers.
- `get_request_statuses(request_ids: Sequence[int])` -> trusted inter-module type/status projections, not salaries or payment credentials.
- `get_approved_claim_statuses(request_ids: Sequence[int])` -> confirmed HR-EIS processing projection, never proof of external bank transfer.

**Inbound contracts**:
1. IAM Fusion auth/session via existing `fusion_auth/client.py`: authenticated `user_id`, `active_role`, effective permissions and module grant. Verified live client methods: `get_users`, `search_users`, `iter_employees`, `employee_page`. Verified module boundary: `modules/directory/contracts.py::get_users`, `get_employees`, `search`. Use the existing plural directory contract, not a fabricated `FakeIam` endpoint. No direct `fusionlab` access. `globals_designation` is used read-only during planning, not queried by HR-EIS business logic.
2. Staff directory/HR master identity projection: `UserDTO` supplies `user_id`, `kind`, `department`, `email`, name and `is_active`; employee enumeration filters inactive rows; it does **not** expose a designation/office assignment or retirement status. Route-policy input and role identity must therefore come from the session's acting designation and an approved HR service-record source (or a separately approved IAM projection extension). Never infer missing designation/retirement fields from employee names or directly query ERP.
3. Dashboard + official-email infrastructure: HR-EIS can produce scoped outbox messages; the transport must be an agreed existing platform adapter. If no contract exists, mailbox delivery and cross-shell notification integration are an explicit external blocker (BR-HR-024/033; UC-021/022), not a fake "sent" flag.
4. Finance/payroll: accept verified status/acknowledgement from an agreed external integration where available. Never calculate payroll, change salary structures, initiate money movement or claim that a locally recorded status is external settlement (BR-HR-027/031/035). Names, authentication, retry contract, reconciliation path and whether endpoint already exists require approval.
5. Secure document storage for claim forms: use existing approved attachment service/storage only after verified; otherwise treat claim-document workflow as blocked pending a secure service choice. No ad-hoc publicly accessible media files.

**Isolation and authentication:** no cross-module FK and no SQL writes to IAM/ERP. Directory contracts may refresh cached identities from IAM; unresolved identity prevents the business write. Outbox + Celery provide idempotent delivery. Missing external dependencies must fail visibly to the authorized actor and preserve pending state. In no case reveal another employee's record existence to an unauthorized caller.
