1. Objective and approach

Assignment 6B asks the team to treat a Phase-1 AI-generated ELM module as inherited software: understand it, test and review it against the complete ELM specifications, improve it while preserving its original version, and verify the result.

The inherited ELM implementation was a small backend leave-request API without an employee-facing ELM workflow. Phase 2 continued from the preserved Phase-1 baseline in a separate branch. The specifications were reviewed for lifecycle, overlap, half-day, printable-application, entitlement, calendar, hierarchy, substitute, and post-approval workflow requirements.

Specification sources reviewed

  • ELM Problem Statement v1.4
  • ELM Use Case Specifications v1.4
  • ELM Business Rule Specifications v1.4
  • ELM Functional Requirement Specification v1.5 and traceability materials
  • ELM Workflow Specifications v1.6
  • Fusion Base Code contracts and the supplied Fusion System Administrator package

Fusion integration surfaces changed

  • ELM server registry and role grants for employee leave-request capabilities.
  • Server-driven navigation and client route registration for the ELM page.
  • API serializers, viewset behavior, leave data model, event history, and migrations.
  • OpenAPI schema, generated permission catalogue, and repository README.

ELM-specific regression scenarios

  • Staff and faculty self-submission; submitted owner is taken from authenticated identity.
  • Requests belonging to another employee are not readable, withdrawn, or deleted by the caller.
  • Permission and module grants are enforced.
  • End date preceding start date is refused.
  • Overlaps with both pending and approved leave are refused; rejected leave does not block.
  • First-half and second-half single-day CL are accepted together; duplicate half and other overlaps are refused.
  • Half-day selection is refused for non-CL or multi-day requests.
  • Submitted requests are immutable; pending requests can be withdrawn and history records both transitions.

4. Runtime and integration limitations

Authentication integration was not end-to-end verified. The local app is configured to contact the ERP-user IAM at http://127.0.0.1:8001. No service was listening on that port during the local run. The supplied Administration package documents a separate operator console and does not provide the ERP-user IAM login contract required by this application.

The backend started and passed Django checks. The frontend served successfully. An unauthenticated call to the protected ELM endpoint returned 401, which confirms the authorization boundary is active, but does not demonstrate a successful logged-in user journey. The client lint script was not verified in this run because the project's ESLint executable was unavailable in the earlier check.

6. Overall assessment

Phase-2 progress: verified partial improvement. The inherited implementation now has a functional, authorization-scoped employee request slice, stronger lifecycle and overlap rules, a printable representation, and regression evidence. Phase 1 remains preserved at d1cb96a; Phase 2 is at c3ab25c.

Deployment readiness: not achieved. Major leave rules, approval workflows, calendar/hierarchy integrations, and authenticated runtime validation remain open. No claim is made that the module satisfies the complete ELM specification or is production-ready.
