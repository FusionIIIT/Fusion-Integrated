## (b) Domain model

### Ownership and identity

HM operational records belong in `fusion_integrated`. IAM owns identity, authentication, designations, module grants, permission grants and role switching. HM stores people only as plain integer `user_id`; no `Employee`, `Student`, `Role`, `Permission`, `UserRole` or `ModuleAccess` model and no cross-module foreign key is proposed. HM-specific Warden/Caretaker-to-hostel responsibility is an operational assignment, not an institute-wide designation. Whether and how that HM assignment is linked to a corresponding IAM designation is unresolved. A Student-to-hostel association cannot be designed until its authority and ownership are decided.

## (c) State machines

Transitions are implemented as declarative `(source state, event, actor kind) -> target state` tables in pure Python. Service functions lock the aggregate and apply the transition, scope, actor, audit and outbox writes in one database transaction. Terminal states cannot be changed through ordinary transition APIs. Room capacity checks and occupancy updates are in that same transaction with database constraints as the concurrency backstop.

| Workflow | Declarative transitions from specification | Enforcement and limits |
|---|---|---|
| BW-HM-01 Accommodation request to initial allotment | No active request —Student submit→ Accommodation Request Submitted; Submitted —Super Admin records initial allotment→ Room Allotted, with defined-capacity guard. | Room assignment service and capacity lock. Re-allotment/formal vacation are separate UCs, not invented workflow steps. |
| BW-HM-02 / BW-HM-03 / CW-HM-01 Leave decision | No active request —Student submit→ Leave Request Submitted; Submitted —Caretaker approve→ Leave Approved; Submitted —Caretaker reject→ Leave Rejected. Composite CW contains both basis paths. | Only an assigned caretaker may decide; request/decision history retained. |
| BW-HM-04 / BW-HM-05 / CW-HM-02 Complaint handling | No complaint —Student submit→ Complaint Submitted; Submitted —Caretaker resolve→ Complaint Resolved; Submitted —Caretaker update→ Complaint Updated — Unresolved; Submitted or Updated —Caretaker escalate when supported→ Complaint Escalated to Warden; Updated —Caretaker resolve→ Complaint Resolved. | Event/history is append-only. Escalation remains conditional on the stated HM/integration scope. No central complaint endpoint is assumed. |
| BW-HM-06 / BW-HM-07 / CW-HM-03 Guest booking decision | No active request —Student submit→ Guest-Room Booking Request Submitted; Submitted —Caretaker approve after availability review→ Guest-Room Booking Approved; Submitted —Caretaker reject after review→ Guest-Room Booking Rejected. | Availability and concurrent approval must be transactional; booking time/overlap semantics remain open. |
| BW-HM-08 / BW-HM-09 / CW-HM-04 Extended-stay decision | No active request —Student submit→ Extended-Stay Request Submitted; Submitted —Warden approve→ Extended-Stay Approved; Submitted —Warden reject→ Extended-Stay Rejected. | Charge/compliance data is not a transition precondition until its provider and semantics are decided (`ISS-HM-014`). |

The workflow specifications do not define transitions for every listed UC. Other writes use a single transactional service per state change, with only explicit requirements implemented. No annual or semester-wise room-allocation cycle is specified.

### Navigation and client route guard plan

Every navigation item has a `required_permission`; every page route has a matching `RequirePermission` guard unless it is genuinely shared by all module-granted roles, in which case every action is gated with `can()`. A page can contain modal/drawer details but no detail-only route. Navigation is server-filtered for the active designation. No internal module shell, sidebar, header, profile, role switcher or duplicate notification bell is built.

The client route families are: `/hm` hostel dashboard; `/hm/hostels` master administration; `/hm/assignments` responsibility bindings; `/hm/accommodation` student request and office allotment; `/hm/rooms` availability/occupancy and assignment history (room creation blocked until its authorized actor and permission are established); `/hm/attendance`; `/hm/leave`; `/hm/complaints`; `/hm/guest-bookings`; `/hm/extended-stays`; `/hm/fines`; `/hm/inventory`; `/hm/staff` (all staff-coordination operations blocked pending ownership and directory decisions); `/hm/guard-shifts`; `/hm/notices`; `/hm/reports`. There is no notifications route. These route families group UCs; details open in drawers/modals. Their exact nav items, role visibility and guard codes depend on unresolved exact designation/permission decisions. Routes must not ship until each has a nav item and a corresponding guard.

Proposed one-to-one client nav/route guards are `hm.hostel.view` for `/hm/hostels`, `hm.hostel_role_binding.view` for `/hm/assignments`, `hm.accommodation_request.view` for `/hm/accommodation`, `hm.room.view` for `/hm/rooms`, `hm.attendance.view` for `/hm/attendance`, `hm.leave_request.view` for `/hm/leave`, `hm.complaint.view` for `/hm/complaints`, `hm.guest_booking.view` for `/hm/guest-bookings`, `hm.extended_stay_request.view` for `/hm/extended-stays`, `hm.fine.view` for `/hm/fines`, `hm.inventory_item.view` for `/hm/inventory`, `hm.staff_coordination.view` for `/hm/staff`, `hm.guard_shift.view` for `/hm/guard-shifts`, `hm.notice.view` for `/hm/notices`, and `hm.report.view` for `/hm/reports`. `/hm` is a redirect to the first authorized route and renders no data without an authorized route. Shared pages must gate controls individually with `can()`; no route guard is treated as server authorization.

For the module-only client registry: code `hm`, base path `/hm`, static import of `../modules/hm/routes`. ## Migration and test strategy

The module will be registered in `DOMAIN_MODULES`, root API URLs, Celery merge, client module registry and `.importlinter` before layers are added. Migration files are HM-owned. Every model index is named and justified by an actual selector filter/order. Constraints protect uniqueness and row-local invariants; room/booking allocation additionally uses a locked service transaction because row capacity and overlap are concurrent cross-row facts. No data migration may query or write IAM/ERP tables. The initial migration must apply on an empty `fusion_integrated` database, reverse cleanly to `hm zero`, reapply, seed modules and report readiness prerequisites. No policy seed is proposed until an actual HM policy is approved.

Planned test suite follows Placement's shape and remains gated on the resolved domain contract:

- Framework-free domain tests cover every validation/calculation branch; state-machine tests enumerate the transition table and reject every illegal actor/state pair.
- HTTP tests use `stub_iam`, `make_session` and `make_principal`, no network/IAM. Every permission-allowed case has a denial twin; test permission strings are asserted against the registry; module grant and action permission are denied independently; active-role switching is tested.
- Ordinary student and unassigned/optional-field-empty principals are covered first. Scoping tests prove cross-student and cross-hostel isolation through list, filter, search, detail and export, with 404 for foreign IDs.
- Concurrency tests with transaction-enabled real DB threads and a barrier cover room capacity/allocation, active assignment uniqueness, overlapping guest bookings if their time semantics are approved, and any other once-only decision. Every thread closes its connection.
- Query-budget tests compare two and twenty rows for every list endpoint. Schedule tests assert merged Celery registration and run each task twice and concurrently to prove outbox delivery is idempotent.
- HTTP journey tests cover each of the 38 active UCs' main scenario and every specified alternate/exception path. Each live ID is cited by a test name or one-line source ID comment. The blank matrix is not converted into invented test-to-requirement mappings.
- The prompt's coverage floors are 90% branch coverage for `modules/hm` and 95% for `modules/hm/domain`, excluding tests/spec if those arrive later. Five highest-risk rules are broken on purpose and the intended tests must fail.
- Frontend hooks test at the shared HTTP boundary. Each route page tests loading, empty, API error, absent unauthorized control, and primary action/refusal. Guard tests pair routes with nav permissions. `make check-client` is required. E2E specs use the repository harness, role/label selectors, sidebar navigation and unique UI-created records; direct deep links for guarded pages must show `NotPermitted`. Browser walkthrough covers each role and plain student, with a keyboard-only journey, and records actual output only.

No test/tool/dependency is added beyond the builder prompt without written approval. The 38-use-case Playwright requirement, deployment walkthrough and fresh-install proof occur only after the approved implementation exists.
